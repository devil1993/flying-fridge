# PWA & Notifications

How **Flying Fridge** works as an installable, offline-capable **Progressive Web
App**, and how it delivers **push notifications** via **Firebase Cloud
Messaging (FCM)**. The app is **mobile-first**, so install and push are core to
the experience.

> Tooling is decided in `docs/adr/`: **`vite-plugin-pwa` (Workbox)** for the
> app-shell/offline layer and **Firebase Cloud Messaging** for push. This
> document is the design, not the decision record.

## 1. Two service workers, two jobs

Flying Fridge uses **two** service-worker concerns:

1. **Workbox SW** — generated by `vite-plugin-pwa` at build time. Owns
   precaching, runtime caching, offline app-shell, and update flow.
2. **`firebase-messaging-sw.js`** — a hand-written worker served from the site
   root (`public/firebase-messaging-sw.js`) that FCM requires to receive
   **background** push messages.

These must **coexist** without clobbering each other. Configure
`vite-plugin-pwa` so its generated worker does not overwrite or unregister the
FCM worker (e.g. keep the FCM worker as a separate static file and, if using
`injectManifest`, either merge the FCM `importScripts` into the Workbox worker
or ensure both register at their own scopes). Getting this right is the main
integration risk; it is called out here deliberately.

## 2. Web App Manifest & install

`vite-plugin-pwa` generates the web app manifest from config in
`vite.config.ts`. Intended contents (mobile-first):

- `name` / `short_name` — "Flying Fridge" / "Fridge".
- `start_url` — the app entry (respecting the SPA route).
- `display` — `standalone` (feels like an installed app).
- `theme_color` / `background_color` — aligned with the light/dark theme
  tokens.
- `icons` — a full set (192/512 + maskable) served from `public/`.
- `orientation` — `portrait` leaning, since phones are the primary medium.

**Install flow:** on a supported browser the manifest + a registered service
worker make the app installable. The app may surface a custom "Add to Home
Screen" prompt by capturing the `beforeinstallprompt` event and offering it at a
sensible moment (not on first paint). HTTPS is mandatory for install (and for
FCM).

## 3. Offline & caching strategy (Workbox)

Goal: the app **opens and is usable offline**, and data syncs when back online.
Two cooperating layers:

**A. App shell (Workbox / vite-plugin-pwa)**
- **Precache** the built JS/CSS/HTML/icon assets (the shell) so the app boots
  with no network.
- **Runtime caching** by resource type:
  - App shell / navigation → **precache + offline fallback** (shell serves for
    SPA routes).
  - Static images/icons/fonts → **cache-first** with expiration.
  - Any same-origin non-critical GETs → **stale-while-revalidate**.
- **Do not** try to cache Firestore/Auth/FCM traffic in Workbox — that is
  Firebase's job (below). Exclude Firebase endpoints from runtime caching.

**B. Data (Firestore local persistence)**
- Firestore's **offline persistence** caches documents locally, serves reads
  offline, and **queues writes** to replay when connectivity returns. This is
  what makes item boards work on a flaky phone connection — Workbox handles the
  app, Firestore handles the data.

**Update flow:** when a new build ships, the new Workbox worker installs in the
background. The app should detect the waiting worker and prompt the user to
refresh (or auto-update on next launch) so families aren't stuck on stale
assets.

## 4. Push notifications with FCM

Push powers reminders/nudges (e.g. task due, pantry expiring, "marked found").
The flow has a foreground path and a background path.

### 4.1 The FCM service worker

`public/firebase-messaging-sw.js` initializes a minimal Firebase app and the
Messaging SDK, then handles **background** messages by showing a notification.
Sketch (provisional):

```js
// public/firebase-messaging-sw.js
importScripts('https://www.gstatic.com/firebasejs/<ver>/firebase-app-compat.js');
importScripts('https://www.gstatic.com/firebasejs/<ver>/firebase-messaging-compat.js');

firebase.initializeApp({ /* messagingSenderId + apiKey + projectId + appId */ });

const messaging = firebase.messaging();
messaging.onBackgroundMessage((payload) => {
  self.registration.showNotification(payload.notification.title, {
    body: payload.notification.body,
    icon: '/icons/icon-192.png',
    data: payload.data, // e.g. deep-link to the item
  });
});
```

> Note: the FCM worker cannot read Vite `import.meta.env`; it is static and
> served as-is. Its Firebase init values are the same public web-config values,
> injected at build time or inlined. The **VAPID key is used from the app
> (§4.3), not from this worker.**

### 4.2 Requesting permission

Notification permission is requested from the **app**, at a contextual moment
(e.g. after the user opts into reminders — not on first load, which mobile users
dismiss). On grant, we register a token; on deny, the app degrades gracefully
(no push, everything else works).

### 4.3 Registering a device token (VAPID)

From `lib/firebase`, using the Messaging SDK:

```ts
import { getToken } from 'firebase/messaging';

const token = await getToken(messaging, {
  vapidKey: import.meta.env.VITE_FIREBASE_VAPID_KEY,
  serviceWorkerRegistration, // the registered firebase-messaging-sw.js
});
// persist `token` on the user's profile (users/{uid}.fcmTokens[])
```

- The **VAPID key** comes from the env contract as **`VITE_FIREBASE_VAPID_KEY`**
  (the "Web Push certificates" key pair generated in the Firebase console —
  provisioning is a manual human step in `human-instructions/`).
- The returned token is stored on the user's Firestore document
  (`users/{uid}.fcmTokens`) so a future sender (Cloud Function / server / manual)
  can target that device. Tokens rotate — refresh and de-duplicate them, and
  prune stale ones.

### 4.4 Foreground vs. background messages

| App state | Handled by | Behavior |
| --- | --- | --- |
| **Foreground** (tab focused) | `onMessage` in the app (Messaging SDK) | No OS notification is shown automatically. The app decides — e.g. an in-app toast, a badge, or a manual `showNotification`. |
| **Background / closed** | `onBackgroundMessage` in `firebase-messaging-sw.js` | The worker shows an OS notification; clicking it should deep-link into the relevant item/board. |

Handle notification **clicks** in the FCM worker (`notificationclick`) to focus
an existing tab or open the app at the item referenced in `payload.data`.

## 4.5 In-app notification feed (implemented today)

Before any push infrastructure, Flying Fridge ships a **real-time in-app
notification feed** that works with zero server code and no Blaze plan
(requirement-5, ADR-0013):

- A family-scoped, append-only **`notifications`** Firestore collection. Each
  board writes one entry when an item is added (`notifyItemAdded`), and every
  member subscribes via `onSnapshot` — so a bell + unread badge in the top bar
  update **live** while the app is open. See
  [`data-model.md`](./data-model.md) §6e for the document shape.
- **Read state** is per-user and local (a `lastSeen` timestamp in
  `localStorage`) — no writes, no contention.
- **Tab alive but unfocused:** when a new entry arrives, `document.hidden` is
  true, and the user has granted permission, the app raises a one-off
  `new Notification(...)` (an OS toast). This is the closest a *page-alive* PWA
  gets to "background" alerts.

### What "run in the background" actually requires

A key limitation to be honest about: **a PWA cannot keep a Firestore listener
running once the app/tab is fully closed.** Service workers are event-driven and
get killed by the OS; they can't hold an open socket to poll Firestore. The
`notifications` feed above therefore only fires while a tab (foreground or
backgrounded) is alive.

To deliver alerts when the app is **closed**, the OS/browser push service must
wake the `firebase-messaging-sw.js` worker via **FCM web push** (§4). That
requires a **server-side sender**: something that, on a new `notifications`
write, looks up the family members' `users/{uid}.fcmTokens` and calls the FCM
send API. The natural implementation is a **Cloud Function** triggered on
`notifications/{id}` create — which needs the **Blaze** plan. Until that exists,
push-while-closed is unavailable; the in-app feed and the tab-alive OS toast are
what work. This staging (feed now, push later) is deliberate and additive.

## 5. Full config contract

FCM needs both the standard web config **and** the VAPID key. The app reads
these from Vite env (`import.meta.env.*`); the FCM worker reuses the public
values inline:

```
VITE_FIREBASE_API_KEY
VITE_FIREBASE_AUTH_DOMAIN
VITE_FIREBASE_PROJECT_ID
VITE_FIREBASE_STORAGE_BUCKET
VITE_FIREBASE_MESSAGING_SENDER_ID    ← required by Messaging
VITE_FIREBASE_APP_ID
VITE_FIREBASE_MEASUREMENT_ID
VITE_FIREBASE_VAPID_KEY              ← required by getToken() for web push
```

`.env` is never committed; `.env.example` documents these names. Firebase is not
provisioned yet, so real values are added during the manual setup step.

## 6. Constraints & notes

- **HTTPS required** for service workers, install, and push (localhost is
  exempted for dev).
- **iOS caveats:** installed web-app push has historically been limited/late on
  iOS Safari; treat push as an **enhancement** and never gate core flows on it.
- **Sending messages** is out of scope for the frontend beyond token
  registration. The intended trigger is now concrete: a **Cloud Function on
  `notifications/{id}` create** that fans out FCM push to members'
  `fcmTokens` (Blaze plan). The in-app feed (§4.5) already writes those docs, so
  push becomes a purely additive backend step.
- **Testability:** the token-registration and permission logic live in
  `lib/firebase`/a feature hook and should be unit-testable with the SDK mocked
  (Vitest).
